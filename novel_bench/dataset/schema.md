# 数据集字段说明

一部作品一个文件：`dataset/works/NN_<id>.yaml`。
`python novel_bench/bench/cli.py check` 会逐条校验，任何一条不过都会打印文件名与字段。

---

## 顶层（作品）

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✓ | 唯一标识，小写英文/下划线；用例 id 以它为前缀更易读 |
| `title` / `title_en` | ✓ / — | 书名；英文名用于报告 |
| `author` | ✓ | 作者 |
| `year` | — | 初版年（字符串，避免 YAML 当数字） |
| `country` | ✓ | 国别（中国 / 英国 / 美国 / 俄国 / 日本 / 哥伦比亚…） |
| `language` | ✓ | 原文语言代码（zh / en / ru / ja / es） |
| `category` | ✓ | `古典` / `现代` / `当代` / `网络` |
| `medium` | ✓ | `出版` / `网络` |
| `genres` | ✓ | 3–4 个类型标签，第一个作为主类型 |
| `representativeness` | ✓ | 2–4 句：为什么这部值得收。**不是简介，是入选理由** |
| `license` | — | `public_domain` / `in_copyright_short_quote`；决定能否附原文摘录 |
| `bible` | ✓ | 设定集，见下 |
| `cases` | ✓ | 1–2 个用例，见下 |

## bible（设定集）

写进主程序 `设定集/` 的原料，控制在 700–1200 字。写多了会挤掉提示词里别的内容。

| 字段 | 必填 | 说明 |
|---|---|---|
| `worldview` | ✓ | 400–800 字：世界规则、时代、地点、当下局势、这一场发生前的状态 |
| `rules` | — | 3–5 条硬约束，原样进 prompt 最前面。写"不许什么"，比写"要什么"有效 |
| `places` | — | `{名称, 说明, 方位?, 内里?}`；`说明` 要能用来判断"这里适合发生什么" |
| `people` | ✓ | 至少 2 人（建议 3–5）。字段：`姓名` `身份` `性格`（必填）、`口癖` `秘密` `目标` `红线` |
| `relations` | — | `{甲, 乙, 关系}`；甲乙必须是 `people` 里出现过的姓名 |
| `foreshadows` | — | `{编号, 内容}`；只放"已经埋下、还没回收"的线 |
| `details` | — | `{名称, 说明}`；器物、习俗、小规矩——日常故事多半靠这些推动 |
| `style` | — | 见下 |

### style

| 字段 | 取值 | 作用 |
|---|---|---|
| `pov` | `第一人称` / `第三人称限知` / `第三人称全知` / `多视角` / `书信` / `剧本` | 进规则，也是"视角漂移"判据的依据 |
| `era` | `premodern` / `modern` / `contemporary` / `fantasy` / `dystopia` / `steampunk` / `historical` | `premodern` 会启用自动现代词表 |
| `sentence` | 一句话 | 句法特征 |
| `diction` | 一句话 | 用词/腔调 |
| `dialogue` | 一句话或"高/中/低" | 对白密度 |
| `taboos` | 词表 | 一个字都不许出现（时代错置、作品禁忌） |

## cases（用例）

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✓ | 唯一，建议 `作品前缀-序号`，如 `hlm-01` |
| `cut` | ✓ | `开篇` / `中段` / `转折` / `高潮前` / `收束` |
| `at` | — | 出自第几回/章，便于人工核对 |
| `story_time` | — | `HH:MM`，作为推演的起始时钟 |
| `place` | ✓ | 必须是 `bible.places` 里的名称（或至少一致） |
| `present` | ✓ | 在场人物，必须都出现在 `bible.people` |
| `focus` | — | 这一场主要考什么（自由标签，进报告） |
| `previously` | 非开篇必填 | 150–300 字前情提要：只讲"读者需要知道的"，不讲"将要发生什么" |
| `scene_seed` | ✓ | 100–200 字：此刻正在发生什么、停在哪一句、谁在场 |
| `ground_truth.hard` | ✓ | **3–5 条硬约束**：所有合法走法都不许踩的线。只写"不许…"，不写"必须…" |
| `ground_truth.beats` | ✓ | 4–6 条，作者实际写下的后续，一条一个动作/转折 |
| `ground_truth.alternatives[]` | ✓ | **1–2 条同样成立的走法**（加上作者那条，总共 ≥2 条路径）|
| `ground_truth.excerpt` | ✓ | 300–500 字。公版可摘原文；在版权期内写**忠实复述**（不复制长段） |
| `ground_truth.divergence_note` | — | 说明"什么必须接住、什么可以自由"。这条直接影响评分的合理性 |

## `ground_truth.hard` 与 `alternatives`（多合法走法）

> 起因：用户明确说 **"我这个软件是给作者提供创意用的，所以我不追求跟原文完全相同。
> 在合理的范围内有变化也是一个重要的功能"**。
>
> ⇒ 一个用例不能只有"答案"，必须有**几条都成立的路**。评测问的不再是"像不像原文"，
> 而是"**有没有踩硬约束**"。

### `hard`（硬约束）

```yaml
    ground_truth:
      hard:
        - 不许让黛玉事先知道来者是王熙凤（她此刻只是纳罕）
        - 不许用现代称谓（小姐/女士/夫人一律不许）
        - 不许出现超自然显灵
```

- 来源必须是**设定**（世界规则 / 时代 / 称谓 / 已知事实），**不是原文情节**。
- 只写"不许…"。`check` 会拦"必须…"开头的（那等于又给了一个标准答案）。
- 3–5 条够了。写多了会把推演框死，和"鼓励变化"自相矛盾。

### `alternatives`（另一条同样成立的路）

```yaml
      alternatives:
        - stance: 凤姐先问月例银子、不夸黛玉容貌（把她的算账脑摆到台面上）
          why_valid: 凤姐是当家人，第一反应可以是"往后要吃穿用度"而不是"这人好看"；
                     这与她"把差事办得漂亮"的目标一致，也不踩任何硬约束。
          beats:
            - 王熙凤进来先向贾母请安，再回头问婆子月例发到哪一房
            - 她打量黛玉，说的是"四季衣裳照着姑娘们的例子添"
          excerpt: |          # 可选：这一条的具体文本
            ……
```

| 字段 | 必填 | 要点 |
|---|---|---|
| `stance` | ✓ | 写**取径**（"先问月例"），**不写**评价（"更好的写法"）。后者会把评委往一个方向带 |
| `why_valid` | ✓ | 凭什么它算合格 —— 评委据此判断"待评文本走这条路行不行" |
| `beats` / `excerpt` | 至少一个 | 这条路的实际内容 |

### 三条判断标准

1. **两条路必须真的不同**。如果第二条只是第一条换个说法，它没有提供信息。
2. **不许写成"更好"**。alternatives 是**并存的可能**，不是升级版。
3. **`check` 会强制**：缺 `hard`、缺 `alternatives`、`stance` 为空、
   有 `beats`/`excerpt` 都空 —— 每一条都报错，不放宽成 warning。
   （2026-10-18 曾把这些校验误插进 `find_case()`，导致**从来没执行、`check` 假绿**；
   现在由 `tools/verify_bench_tool.py` 的 B1 守着。）

## 三条写作纪律

1. **前情只给已知，不给预告。** `previously` 里出现"后来""即将"就把答案泄了。
   真实后续写进 `ground_truth`——它在装配时会被主程序截掉（只保留「起」段），
   不会进人物提示词。这是本工具防泄漏的唯一机制，破坏它整套评测就失效。
2. **`scene_seed` 要停在动作中间。** "她推开门，看见……"比"她走进房间"更能逼出下一拍。
3. **`divergence_note` 写清判据。** 例如"允许不用原句，但三步骨架不能缺"。
   没有这一条，评委容易拿"和原文不一样"当缺点。

## 命名与目录

- 文件名：`NN_<id>.yaml`，`NN` 只用于排序，不参与任何逻辑。
- 图片、原文、参考资料一律不入库；数据集只有文本。
- 新增作品后先 `check`，再 `smoke --case <id>`，两步都过再进 `presets.yaml`。
