# 评审模型选型

本工具里有两个"用模型"的地方，**必须分开看**：

| 用途 | 谁决定 | 在哪配 |
|---|---|---|
| **生成**：真正跑推演 | 主程序（`NovelWorldSimulator/.env` 与 `llm_models.json`） | 与本工具无关 |
| **评审**：给推演稿打分、做盲评 | 本工具 | `novel_bench/.env` 的 `NB_JUDGE*` |

评审模型**不要**跟推演模型用同一个。同源模型会偏爱自己的句式（尤其是排比、四字词、
"不是……而是……"这类腔调），盲评会失真。至少换一个厂商。

---

## 1. 结论先行

| 场景 | 推荐 | 理由 |
|---|---|---|
| 默认 / 日常回归 | **DeepSeek-Chat** 或 **Qwen-Max** | 中文语感够用，价格低到可以每次改完都跑；JSON 稳定 |
| 要下结论（发布前） | **Claude Sonnet 系** | LitBench 的零样本评委里与人类偏好一致率最高（约 73%） |
| 中文母语审美 | **Qwen-Max / GLM / Kimi** | 对成语、称谓、文言的判断比英文模型细 |
| 三评委中位数 | Claude + Qwen + DeepSeek | 覆盖英式克制、中文语感、性价比三档，抵消单模型偏好 |

不建议：

- **推理型模型**（o 系、R1 系）当评委：会把评分当推理题，输出冗长、偏形式，
  而且常常不按 JSON 交卷。实测在 `verify_progress_eval` 里也踩过同类问题。
- **7B 级小模型**：给不出稳定的 6 维分数，同一段文本两次评分能差 1.5 分。
- **同一个模型既生成又评审**：见上。

---

## 2. 依据

1. **LitBench（2025, arXiv:2507.00769）**：在 2480 对人工标注的故事比较上测零样本评委，
   Claude-3.7-Sonnet 与人类偏好一致率约 73%，是当时最强的现成评委；专门训练的奖励模型约 78%。
   ⇒ 成对比较这件事，前沿通用模型已经够用；绝对打分更不可靠。
2. **WebNovelBench（2025, arXiv:2505.14818）**：用 LLM-as-Judge 给中文网络小说的八个叙事维度打分，
   再把分数映射到人类作品的百分位。它的做法说明：**中文长文评审可行，但必须多维、必须对照**。
3. **G-Eval（2023, arXiv:2303.16634）**：给评分表 + 让模型先写理由再打分，比直接问稳定；
   温度必须为 0，否则同一文本两次分数会漂。
4. **MT-Bench 的偏置研究（2023, arXiv:2306.05685）**：评委偏爱第一个出现的答案、偏爱更长的答案。
   ⇒ 交换顺序（本工具已做）；长度靠 `NB_JUDGE_MAX_CHARS` 截齐，避免"写得长就赢"。

关于"中文 vs 英文模型谁更懂中文小说"：公开横评（如 2026 年的写作类榜单）普遍把
Claude 系排在"文笔与语气"首位，把 Qwen/GLM 排在"中文母语表达"前列。
两者结论不冲突——前者评的是"这段文字作为小说好不好"，后者评的是"这句话像不像中国人写的"。
本工具的 rubric 两项都涉及，所以建议评审团里各放一个。

## 2.5 新版 DeepSeek Flash 默认会思考（2026-10 实测）

`deepseek-flash` 是滚动别名：`GET /v1/models` 只返回 `deepseek-flash` 与 `deepseek-v4-pro`
两个名字，没有带日期的快照 id。新版与旧版最明显的区别是**默认输出思考内容**：

| 同一条"写 300 字小说"的提示 | 耗时 | 输出 token | 思考试 | 正文 |
|---|---|---|---|---|
| 默认（思考开） | 6.1s | 900（撞上限） | 900 | **0 字**，finish=length |
| 加 `thinking:{"type":"disabled"}` | 1.9s | 217 | 0 | 256 字 |

⇒ 短预算（<2000 token）的**结论型**任务必须关思考，否则正文一个字都拿不到。
本工具默认按模型名自动关（`NB_JUDGE_THINKING=auto`）。

主程序侧（2026-10-18 起）有三层：
1. `LLM_THINKING_MODE` = `auto / off / always` —— **总开关**，
   界面在「天问 · LLM 接入 → 没填就用这三项 → 思考模式」，改完下一拍生效。
2. `NO_THINK_PURPOSES` —— 写死的"结论型用途"清单（进度判定、类型判定、当天地图…），
   `auto` 模式下只关这些。
3. `LLM_NO_THINK_RETRY` —— 正文一个字都没拿到时，自动关思考重试一次（默认开，
   `always` 模式下也保留：要"思考"不等于接受"一个字都没有"）。

`off` **不会**绕过"这个模型认不认 `thinking` 参数"那道闸：给 Claude / Qwen 发仍然不发
（会 400）。这条由 `detect_thinking_switch()` 守。

## 3. 配置写法

```dotenv
# 主评委
NB_LLM_BASE_URL=https://api.deepseek.com/v1
NB_LLM_API_KEY=sk-...
NB_JUDGE_MODEL=deepseek-chat

# 第二评委（可选）：换厂商，覆盖另一种审美
NB_JUDGE2_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
NB_JUDGE2_API_KEY=sk-...
NB_JUDGE2_MODEL=qwen-max

# 第三评委（可选）：要下结论时开
NB_JUDGE3_BASE_URL=https://openrouter.ai/api/v1
NB_JUDGE3_API_KEY=sk-or-...
NB_JUDGE3_MODEL=anthropic/claude-sonnet-4.5
```

只要是 OpenAI 兼容的 `/chat/completions` 就能用：DeepSeek、通义、智谱、Kimi、豆包、
OpenRouter、vLLM、Ollama（`http://localhost:11434/v1`）都可以。
配了多个评委时，每个维度取**中位数**，报告里保留每个评委的原始分。

## 4. 成本估算

单用例的评审调用：`sim` 分项 1 次 + `ref` 分项 1 次 + 盲评 2 次 = **4 次/评委**。
输入约 2500–3500 token（设定集 + 前情 + 两段文本 + rubric），输出 400–800 token。

| 规模 | 调用数（单评委） | 输入 token | 输出 token |
|---|---|---|---|
| `smoke` 4 例 | 16 | ~50k | ~10k |
| `core` 14 例 | 56 | ~180k | ~35k |
| `full` 28 例 | 112 | ~350k | ~70k |

按 2026 年公开价粗算（价格会变，仅作量级参考）：

- DeepSeek：全量一次约 **¥1–3**
- Qwen-Max：约 **¥10–20**
- Claude Sonnet：约 **$2–4**

推演本身比评审贵得多：一个用例 8 拍，每拍 1–2 次生成调用，加上开场（约 14 次），
大约 25–30 次调用；`full` 一轮是 700–900 次生成调用。评审通常只占整轮成本的 5%–10%。

## 5. 换评委时的纪律

1. **不要跨评委比较历史分数**。报告里的 `sim_mean` 只在同一评委、同一温度下可比。
2. 换评委后，**重跑一次基线**（当前产品版本），再谈优化前后。
3. 若两个评委结论相反（一个说变好一个说变差），看 `dims`：通常是某一维度的口径分歧，
   例如中文评委更看重称谓准确，英文评委更看重节奏。
4. 报告归档时把 `.env` 里的模型名一起抄进笔记——`summary.json` 不记录密钥，但记录不了你的口头配置。
