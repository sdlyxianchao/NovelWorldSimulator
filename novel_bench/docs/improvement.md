# 优化改进手册

按"报告里的症状"索引到"该动哪一层"。每一条都来自这个项目真实修过的 bug，
不是通用建议——所以先照着查，再想新办法。

> 用法：跑完 `report`，先在 `summary.json` 里找到对应的症状，再翻到下面那一节。
> 改完只跑 `smoke`（4 例）确认没崩，再跑 `core`（14 例）判断趋势。
> 不要一次改两处——两次改动混在一轮里，分数变了也说不清是谁的功劳。

---

## 1. `chars` 很少、`entries` 很少

**症状**：一个用例只有几百字，`hygiene` 反而挺高（因为没内容可重复）。

**先查上游给了多少**，不要先怪模型不会写：

1. `cases/<id>/meta.json` 的 `ticks_done` 是否等于 `ticks_requested`。
   不等 ⇒ 超时或被停，看 `timed_out`。
2. 主程序日志里当天剧本、样章的长度。若样章有 3000 字而实录只有 500，
   问题在"分发/串联"，不在生成。
3. 导出链路上的四层预算（截断长度、token 上限、整份替换、只整理不扩写）——
   这四层各自看都合理，合起来能把 4.4 万字压成 900 字。**按层量字符数**。

**已知教训**：`if not A and B` 这种"二选一"写法是丢内容的经典形态。
剧本模式下完整的一天在 `scenes` 里，`_daily_narrative` 只有几行；
旧代码"lines 非空就不看 scenes" ⇒ 一天 4.4 万字被整理成 900 字。
**要合并，不要二选一**，并且留一条"某一路为空"的成对判据。

---

## 2. `repeat_4gram` 高（> 10%）、`dup_pairs` 多

**症状**：句子读起来"绕"，同一句环境描写反复出现，人物把同一段动作又演一遍。

按可能性排序：

1. **上下文窗口太小**：模型看不到自己上一拍做了什么，只能重演。
   修法是**单独给一条「你上一拍做的」**并明写"不要再演一遍"，
   而不是指望它从六条混合对话里自己挑。
   ⚠ 只取动作型条目；把"心声"也算进去，等于告诉模型"我想过的事已经发生了"。
2. **素材池只有一条**：环境白描按 `day` 做种子 ⇒ 一整天同一句。
   修法是"摊开候选 + 挑没用过的 + 全用过就不写"（少一条远好过多一条重复）。
3. **提示词要求"每一拍都要有环境"**：这会逼模型复读。改成"有变化才写"。

**验证**：`report` 的"文本卫生"表里两项应同时下降；只降一项说明只修了表面。

---

## 3. `meta_marks` 非空

**症状**：正文里出现 `〔action·…〕`、`【aside】`、`◇`、`（并入第 N 条）`、`**加粗**`。

**根因**：提示词里的内部格式被当成内容写出来了。

**修法**：清洗必须放在**词条构造的唯一入口**，不是在导出时补一刀。
台本、界面、原文、参考、小说版本是五个出口，只修导出等于只修最后一个。
⚠ 早退条件要看**全部**正则；只看一条会把"自我指令"放过去。

**验证**：`meta_marks` 必须为 0；再抽读 `transcript.md` 确认没有"半截标记"。

---

## 4. `present_coverage` 低、`cast_coverage` 低

**症状**：叫来了四个人，只有两个说话；或者整场只有主角，配角全是背景。

1. 检查 `case.present` 是否都写进了 `bible.people`（`check` 会报）。
2. 检查人物卡是否有 `目标`/`秘密`：没有欲望的人不会主动开口。
3. 检查调度是否每拍只点一个人。**"每拍全员各说一句"和"每拍只有一人"都不对**，
   要看这一拍有没有理由让第二个人插话。
4. 群像场（如 `hlm-02`、`shz-02`）的 `focus` 写了"群像"，若仍只有两人开口，
   这是调度问题，不是写作问题。

---

## 5. `canon` 低（设定冲突、凭空多出人和地点）

1. 规则（`bible.rules`）是否真的进了 prompt？它们在主程序里是**原样放在最前面**的，
   若被摘要或截断，约束就失效。
2. 信息边界：人物是否知道了不该知道的事。这通常来自"把整条剧情线当前缀"——
   把结局和谜底一起递给模型，它当然直奔结局。修法是只给"起"段。
3. 时代错置（`taboo_hits`）：`style.taboos` 要写全，尤其是"分钟/小时/情绪/状态"这类
   现代抽象词。作品越古，越要写。

---

## 6. `character` 低（所有人都一个腔调）

1. 人物卡的 `口癖` 是不是空的？空口癖 = 没有声音。
2. 提示词里是否给了"✅/❌ 对照例子"？只写"要像这个人"没有用。
3. **同一件事两处实现**：如果两处提示词都在描述人物性格，模型会取交集，
   最后剩下最泛的那几句。找到唯一汇聚函数，只改那里。
4. 遮住名字读一遍实录：认不出是谁说的，就是这一项低。

---

## 7. `prose` 低（模板腔、每句都抒情、形容词堆砌）

1. 先看 `sentence_len_median`：真人 9–13 字。若 20+，说明句子被拉长了，
   常见原因是"要求写得文学一点"这类提示词。
2. 去 AI 味的词表要分 HARD / SOFT：HARD 会被真删，只能放删了不伤句意的词。
3. 给"笔调样本"比给形容词表有效：把同一位作者写得好的一段（≤900 字）递进去，
   注明"只学笔调，内容一个字都不要搬"。
4. **不要用"氛围感""画面感"这类词要求模型**——它们只会换来更多形容词。

---

## 8. `gap` 在某一类作品上特别大

**症状**：`report.md` 底部按 gap 排序，前几名都是同一类（文言、抒情、推理、群像）。

**这说明是体裁适配问题，不是全局退化。** 不要动全局提示词，否则其他体裁一起退。

做法：

1. 把这类作品的 `focus` 与 `divergence_note` 再写细一点，让评委按"这一场该考什么"评。
2. 在 `bible.style` 里把 `pov`/`sentence`/`diction` 写具体（"短句、少形容词"比"文风优美"有用）。
3. 若只有文言作品差，考虑给这类单开一个 `style` 预设，而不是改默认值。

---

## 9. 盲评胜率异常高（> 50%）

先怀疑**评委被长度或格式骗了**：

- 推演实录是分拍记录（有说话人标签），原文是成稿。评委可能更喜欢"信息密集"的那份。
- 检查 `cases/*/judge.json` 的 `pairwise.details`，看两个顺序是否一致；
  只在某一个顺序赢 ⇒ 位置偏置，换评委。
- 若评委与生成模型同源，换一个厂商再跑一遍（见 `docs/models.md`）。

---

## 10. 报告分数与"人读感受"不一致

**以人读为准。** 报告是索引，不是判决。具体做法：

1. 打开 `transcript.md` 读三分钟，记下最刺眼的三处。
2. 对照 `judge.json` 的 `defects`，看评委有没有指到同样的地方。
3. 若评委没指到，说明 rubric 缺一个维度——补 rubric，而不是调分数。
4. 若评委指到了但分数不低，说明权重不对——改 `DIMENSIONS` 的权重，并在
   `docs/methodology.md` 里写明为什么改。

---

## 11. 一次改动的标准流程（照抄）

```bash
# 0) 先确认没坏（0 成本）
python tools/run_all_verifications.py          # 判据（守"会不会崩"）
python novel_bench/bench/cli.py check
python novel_bench/bench/cli.py smoke --preset smoke

# 1) 基线（如果还没跑过）
python novel_bench/bench/cli.py run   --preset core --run-id base
python novel_bench/bench/cli.py judge --run novel_bench/results/base
python novel_bench/bench/cli.py report --run novel_bench/results/base

# 2) 改一处

# 3) 复测
python novel_bench/bench/cli.py run   --preset core --run-id after-<改动名>
python novel_bench/bench/cli.py judge --run novel_bench/results/after-<改动名>
python novel_bench/bench/cli.py report --run novel_bench/results/after-<改动名>
python novel_bench/bench/cli.py compare --a novel_bench/results/base --b novel_bench/results/after-<改动名>

# 4) 把结论写进 results/<run>/NOTES.md（三行：改了什么、哪个指标动了、下一步）
```

`NOTES.md` 不是形式主义：三个月后回看，只有它能把分数和当时的改动对上。
